## 2. What shipped

Version **1.4.4**, build **11**, committed as `2adbe37`. **Not pushed** — `git push` is
yours to run.

Verified green before archiving: build 0 errors, matchkit **78/78**, `matchkit doctor`
clean, ingredient-content validator 620/620, UI suite **14 tests / 0 failures / 1 skip**.

### The one that matters most: search actually ranks now
`LocalCatalogStore.search` led its `ORDER BY` with
`(ingredients IS NULL OR length(ingredients) = 0)`. That column is `NOT NULL` and stores a
DEFLATE blob whose minimum length is 6, so **the key is constant 0 across all 31,142
rows** and ordering had collapsed to `length(name) ASC` — shortest name wins, with no
relevance term at all.

| Query | Was | Now |
|---|---|---|
| `purina` | `FF PTE 12CT WF` | Purina® Kitten Chow® |
| `Nutro` | `Merchandise` | Nutro Max Salmon Dry Cat Food |
| `Cesar` | `Mars Dog Food,` | Cesar® Puppy Wet Dog Food |
| `Purina Pro Plan` | `Beggin' Strips` | Purina Pro Plan Variety Pack |

Two traps caught while implementing, both of which would have shipped a regression:
`tier` is TEXT `S`/`A`/`B`, so the proposed `tier ASC` would have ranked the 306
**best**-described products **last**; and naive prefix matching made `beef` return
"**Beef**eaters", fixed by padding both sides of the match to a word boundary.

## 3. Deliberately NOT done

### `ScanRematchService` stays unwired — do not "fix" this casually
Its only caller, `AppInitializer`, was itself never called, so the matcher improvements in
this release reach **new scans only**; saved history keeps its old verdicts. That is a real
gap, and it is still the right call for tonight:

- Wiring it the obvious way (calling `AppInitializer.initialize()`) **re-runs
  `Superwall.configure` without `shouldPreload = false`** — the setting the code comments
  say took first frame from ~11s down. It also configures Superwall during UI tests.
- Wiring it carefully still leaves an **irreversible, one-shot, main-thread** rewrite of
  every non-allergen saved scan, behind a `UserDefaults` flag, on the exact release whose
  matcher changes guarantee scores move. A user who saved "Excellent 88" would open the app
  to "Caution 62" with no explanation and no rollback. Measured ~2.2 ms/product on Apple
  Silicon, est. 5-7 ms on device → ~1s main-thread hang at 200 scans.
- Because that flag persists in the simulator across `app.terminate()`, **a green UI-test
  run tells you nothing about the next one.**

It needs the compute off the main actor, chunked writes, a progress indicator, something
that tells the owner their history was recalculated, and a deterministic test fixture.
The reasoning is now in the file header.

### Avoidance-group label override rejected
Making an avoidance-group hit emit a `.caution` override would have **silently disabled
App Store review prompts** — `ReviewPrompt.swift:97` gates on `.excellent || .good` — for
every user with a group selected, **with all 78 tests still passing**. This was the single
most dangerous proposal of the night and only the critic caught it.

## 5. Scoring still does not discriminate

Unchanged this release, and it undercuts every score-based paywall audience you write.
Measured over the full catalog (n=31,136):

```
Excellent  18,240  58.6%
Caution    12,684  40.7%
Avoid         211   0.7%
Good            1   0.003%      p50 = 95.3, and 99.72% score >= 75
```

So `user.searched_food_score < 60` addresses ~0.7% of possible foods and `< 80` about 1%.
Any paywall Liquid or audience written against that number is targeting an empty set.
Moving the 75/50/25 thresholds will not fix it — the distribution is 16 points wide from
p1 to p99. It needs the penalty model rebalanced, with `matchkit calibration` and a
transition matrix to show what moves.

A cheap interim win: emit a `searched_food_has_concerns` boolean attribute alongside the
score. That discriminates today and is additive/inert.
